## 1. Умножение матриц: `mul_ijk` и `mul_ikj` (`-O2`)

Исходный код: [`matmul_asm.c`](matmul_asm.c). При `MAXN = 768` одна строка матрицы из чисел `double` (по 8 байт) занимает в памяти $768 \times 8 = \mathbf{6144\text{ байта}}$.

### Внутренние циклы в ассемблере

#### `mul_ijk` (внутренний цикл по `k`)
* **x86-64 ([`x86_64_matmul_matmul_x86_o2.s`](x86_64_matmul_matmul_x86_o2.s), 7 инструкций в цикле `.L4`):**
  ```x86asm
  .L4:
      movsd   xmm0, QWORD PTR [rdx]   ; загрузить a[i][k] (подряд по строке)
      mulsd   xmm0, QWORD PTR [rax]   ; умножить на b[k][j] (из столбца)
      add     rax, 6144               ; шаг по матрице b: +6144 Б (прыжок через строку!)
      add     rdx, 8                  ; шаг по матрице a: +8 Б (соседний элемент)
      addsd   xmm1, xmm0              ; накопить сумму s += a[i][k] * b[k][j]
      cmp     rdx, rcx                ; проверка конца строки
      jne     .L4
  ; После цикла: movsd QWORD PTR [rdi], xmm1 (однократная запись в c[i][j])
  ```
* **RISC-V 64-bit ([`risc_v_matmul_matmul_riscv_o2.s`](risc_v_matmul_matmul_riscv_o2.s), 6 инструкций в цикле `.L4`):**
  ```asm
  .L4:
      fld     fa3, 0(a4)              # загрузить a[i][k]
      fld     fa4, 0(a5)              # загрузить b[k][j]
      add     a5, a5, a2              # шаг по b: +6144 Б (a2 = 8192 - 2048)
      addi    a4, a4, 8               # шаг по a: +8 Б
      fmadd.d fa5, fa3, fa4, fa5      # слитное умножение-сложение s += a[i][k] * b[k][j]
      bne     a5, a3, .L4
  # После цикла: fsd fa5, 0(a0) (однократная запись в c[i][j])
  ```

#### `mul_ikj` (внутренний цикл по `j`)
* **x86-64 ([`x86_64_matmul_matmul_x86_o2.s`](x86_64_matmul_matmul_x86_o2.s), 7 инструкций в цикле `.L16`):**
  ```x86asm
      movsd   xmm1, QWORD PTR [rdi]           ; до цикла: загрузить a[i][k] в регистр
  .L16:
      movsd   xmm0, QWORD PTR b[rcx+rax]      ; читать b[k][j] подряд (+8 Б)
      mulsd   xmm0, xmm1                      ; b[k][j] * a[i][k]
      addsd   xmm0, QWORD PTR c[rax+rdx]      ; прибавить c[i][j] из памяти (+8 Б)
      movsd   QWORD PTR c[rdx+rax], xmm0      ; записать обновлённый c[i][j]
      add     rax, 8                          ; сдвиг индекса на следующий элемент (+8 Б)
      cmp     rsi, rax
      jne     .L16
  ```
* **RISC-V 64-bit ([`risc_v_matmul_matmul_riscv_o2.s`](risc_v_matmul_matmul_riscv_o2.s), 7 инструкций в цикле `.L12`):**
  ```asm
      fld     fa3, 0(a1)                      # до цикла: загрузить a[i][k] в регистр
  .L12:
      fld     fa4, 0(a5)                      # читать c[i][j] подряд (+8 Б)
      fld     fa5, 0(a4)                      # читать b[k][j] подряд (+8 Б)
      addi    a5, a5, 8                       # сдвиг указателя c (+8 Б)
      addi    a4, a4, 8                       # сдвиг указателя b (+8 Б)
      fmadd.d fa5, fa5, fa3, fa4              # c[i][j] + b[k][j] * a[i][k]
      fsd     fa5, -8(a5)                     # записать новый c[i][j] в память
      bne     a5, a3, .L12
  ```

### Ответы на вопросы (Часть 1)
1. **Инструкции загрузки и записи:** на x86-64 используется `movsd` (а также встроенное чтение из памяти в `mulsd` и `addsd`); на RISC-V (строгая Load/Store архитектура) — только `fld` для загрузки и `fsd` для записи `double`.
2. **Адрес `b[k][j]` в `ijk`:** меняется **с шагом в целую строку (`6144` байта)** на каждой итерации (`add rax, 6144` на x86-64; `add a5, a5, a2` на RISC-V, где `6144` собрано как `8192 - 2048`), тогда как `c[i][j]` записывается один раз после цикла.
3. **Обращения к `b[k][j]` и `c[i][j]` в `ikj`:** оба массива читаются и обновляются **строго подряд по одной строке с шагом `+8` байт** (прыжков на `6144` байта нет), а `a[i][k]` держится в регистре весь внутренний цикл.
4. **Число инструкций в теле внутреннего цикла (`-O2`):**
   * `mul_ijk`: **7** на x86-64 против **6** на RISC-V (в RISC-V `fmadd.d` объединяет `mul`+`add`, а `bne` объединяет `cmp`+`jne`).
   * `mul_ikj`: **7** на x86-64 и **7** на RISC-V.
5. **Векторизация на `-O3 -march=native`:**
   * На **x86-64** появляются 256-битные векторные инструкции AVX2 + FMA (`vbroadcastsd`, `vmovapd`, `vfmadd213pd` / `vfmadd231pd` с регистрами `ymm`).
   * На **RISC-V** при `-march=rv64gc` векторизации нет; при включении векторного расширения `-march=rv64gcv` появляются инструкции RVV (`vsetvli`, `vle64.v`, `vfmacc.vf`, `vse64.v`).
6. **Почему `ikj` быстрее при том же числе операций:** процессор подгружает данные из RAM в кэш L1 линиями по **64 байта** (8 чисел `double`). В `ikj` используются все 8 чисел из каждой загруженной линии (пространственная локальность), а в `ijk` прыжок на `6144` байта вызывает промах кэша на каждой итерации.

## 2. Алгоритм Штрассена: рекурсия и стек (`-O2`)

Анализ функции `strassen_rec(sz, A, sa, B, sb, C, sc, work)` и обёртки `strassen` из [`strassen_asm.c`](strassen_asm.c) по листингам [`x86_64_strassen_strassen_x86_o2.s`](x86_64_strassen_strassen_x86_o2.s) и [`risc_v_strassen_strassen_riscv_o2.s`](risc_v_strassen_strassen_riscv_o2.s):

| Элемент | x86-64 (`-O2 -masm=intel`) | RISC-V 64-bit (`-O2 -march=rv64gc`) |
| :--- | :--- | :--- |
| **Пролог `strassen_rec`** | Сохраняет 6 *callee-saved* регистров (`r15, r14, r13, r12, rbp, rbx` = `48` Б) и вычитает `sub rsp, 232` = **`280` байт** (+ `8` Б адрес возврата = **`288` байт**, кратно 16). | Отрезает `addi sp, sp, -304` = **`304` байта** (кратно 16), сохраняет `ra` (`296(sp)`) и 12 регистров `s0..s11` (использует *shrink-wrapping*: сначала сохраняет `ra, s1, s2`, а остальные 10 — только если `sz > 64`). |
| **Эпилог `strassen_rec`** | `add rsp, 232`, 6 команд `pop`, `ret` (`.L1`). | `ld s0..s11, ra`, `addi sp, sp, 304`, `jr ra` (`.L1` / `.L58`). |
| **Передача 8 аргументов** | 6 аргументов в регистрах (`edi..r9`), 7-й и 8-й (`sc`, `work`) кладутся на стек (`push`/`pop` вокруг каждого вызова). | Все 8 аргументов передаются в регистрах **`a0..a7`** без обращения к стеку. |
| **Рекурсивные вызовы** | **7 вызовов** `call strassen_rec` (для $M_1 \dots M_7$). Функции `add_mat`/`sub_mat` встроены (*inlined*). | **7 вызовов** `call strassen_rec` (раскрывается в `auipc` + `jalr` / `jal`). |
| **Вызовы `malloc`/`free`** | Внутри `strassen_rec` — **0** (единый буфер `work` нарезается смещениями). В `strassen` — 1 `call malloc` и хвостовой `jmp free` (плюс 3 `calloc` + 3 `free` при дополнении нулями). | Внутри `strassen_rec` — **0**. В `strassen` — 1 `call malloc` и хвостовой `tail free` (плюс 3 `calloc` + 3 `free` при дополнении нулями). |
| **Базовый случай (`sz <= 64`)** | `cmp r10d, 64` $\to$ `jle .L59`: встроенный `base_mul` (обнуление через `rep stosq` + цикл `ikj`). | `li a0, 64` $\to$ `ble s2, a0, .L61`: встроенный `base_mul` (обнуление через `memset` + цикл `ikj`). |

* **Почему на маленьких матрицах Штрассен проигрывает:** экономия 1 умножения (7 вместо 8) требует **18 дополнительных матричных сложений/вычитаний**, сборки 4 блоков и 7 рекурсивных вызовов. При $n \le 64$ затраты на память и рекурсию превышают выигрыш.
* **Что в ассемблере соответствует накладным расходам рекурсии:** создание/очистка стекового кадра (`280`/`304` Б), десятки инструкций сохранения/восстановления регистров вокруг 7 вызовов (`spilling`), 18 отдельных циклов чтения-записи промежуточных буферов (`.L10`–`.L38`) и выделение кучи (`malloc`/`free`).

## 3. Сравнение двух ISA: `max2` и `max3` (`-O2`)

Исходный код: [`max2_max3_max.c`](max2_max3_max.c).

```c
int max2(int a, int b) { return a > b ? a : b; }
int max3(int a, int b, int c) {
    int m = a > b ? a : b;
    return m > c ? m : c;
}
```

### Листинги (`-O2`)
* **x86-64 ([`x86_64_max_max_x86_o2.s`](x86_64_max_max_x86_o2.s)):**
  ```x86asm
  max3:
      cmp     edi, edx        ; сравниваем a и c
      mov     eax, esi        ; результат = b
      cmovl   edi, edx        ; если a < c, edi = c
      cmp     edi, esi        ; сравниваем max(a, c) и b
      cmovge  eax, edi        ; если max(a, c) >= b, eax = max(a, c)
      ret
  ```
* **RISC-V 64-bit ([`risc_v_max_max_riscv_o2.s`](risc_v_max_max_riscv_o2.s)):**
  ```asm
  max3:
      mv      a5, a0
      sext.w  a0, a0          # знаковое расширение 32-битного int до 64 бит
      bge     a5, a2, .L5     # условный переход, если a >= c
      sext.w  a0, a2
  .L5:
      sext.w  a5, a0
      bge     a5, a1, .L6     # условный переход, если max(a, c) >= b
      sext.w  a0, a1
  .L6:
      ret
  ```

### Сравнительная таблица

| Критерий | x86-64 (`-O2`) | RISC-V 64-bit (`-O2 -march=rv64gc`) |
| :--- | :--- | :--- |
| **Аргументы и результат** | Аргументы: `edi, esi, edx`; результат: `eax`. | Аргументы: `a0, a1, a2`; результат: `a0`. |
| **Переходы vs `cmov`** | **Без переходов:** компилятор использует условные пересылки `cmovl` и `cmovge`, избегая промахов предсказателя ветвлений. | **С переходами:** в базовом `rv64gc` нет команды `cmov`, поэтому используются 2 условных перехода `bge` и инструкции `sext.w` для соблюдения 32-битного знакового представления в 64-битных регистрах. |
| **Размер `max3`** | **6 инструкций** (5 без `ret`). | **8 инструкций** (7 без `ret`). |

## 4. Чтение цикла: `sum` (`-O2`)

Исходный код: [`sum_f_sum_f.c`](sum_f_sum_f.c).

```c
long sum(const long *a, long n) {
    long s = 0;
    for (long i = 0; i < n; i++) s += a[i];
    return s;
}
```

* **RISC-V ([`risc_v_sum_f_sum_f_riscv_o2.s`](risc_v_sum_f_sum_f_riscv_o2.s)):**
  ```asm
  sum:
      ble     a1, zero, .L4   # защитная проверка n <= 0 ДО цикла
      slli    a1, a1, 3       # n * 8 байт
      mv      a5, a0          # текущий указатель ptr = a
      add     a3, a0, a1      # конечный адрес end = a + n * 8
      li      a0, 0           # s = 0
  .L3:
      ld      a4, 0(a5)       # загрузка a[i]
      addi    a5, a5, 8       # сдвиг указателя (+8 Б)
      add     a0, a0, a4      # s += a[i]
      bne     a5, a3, .L3     # проверка условия в конце и переход назад
      ret
  .L4:
      li      a0, 0
      ret
  ```
* **Разбор:** стекового пролога и сохранения `ra` нет (функция листовая, все переменные в регистрах). Компилятор применил **инверсию цикла** (*Loop Inversion*): проверка `n <= 0` вынесена перед циклом (`ble a1, zero, .L4`), чтобы тело не выполнилось при пустом массиве, а проверка продолжения поставлена в конец тела (`bne a5, a3, .L3`). Это сокращает число переходов на каждой итерации с двух до одного и помогает предсказателю ветвлений.

## 5. Чтение функции целиком: `f` (`-O2` и `-O0`)

Исходный код: [`sum_f_sum_f.c`](sum_f_sum_f.c).

```c
long f(long n) {
    long s = 0;
    for (long i = 0; i < n; i++) s += i * i;
    return s;
}
```

* **Сборка с `-O2` ([`risc_v_sum_f_sum_f_riscv_o2.s`](risc_v_sum_f_sum_f_riscv_o2.s)):**
  ```asm
  f:
      mv      a3, a0
      ble     a0, zero, .L4   # проверка n <= 0
      li      a5, 0           # i = 0
      li      a0, 0           # s = 0
  .L3:
      mul     a4, a5, a5      # i * i
      addi    a5, a5, 1       # i++
      add     a0, a0, a4      # s += i * i
      bne     a3, a5, .L3     # проверка i != n в конце цикла
      ret
  .L4:
      li      a0, 0
      ret
  ```
* **Пролог, сохранение `ra`, эпилог и `ret`:**
  * При **`-O2`** стековый кадр не создаётся (**`0` байт**), так как все переменные размещены в регистрах. Регистр **`ra` не сохраняется**, потому что `f` — листовая функция (внутри нет вызовов `call`/`jal`, адрес возврата не перезаписывается).
  * При **`-O0`** (без оптимизации) в RISC-V выделяется кадр **`addi sp, sp, -48`** (**48 байт** на стеке) и сохраняется указатель кадра `sd s0, 40(sp)` (`ra` по-прежнему не сохраняется, так как функция листовая), а в эпилоге выполняется `ld s0, 40(sp)`, `addi sp, sp, 48` и `jr ra` (`ret`).
* **Почему размер кадра стека кратен 16:** стандарты ABI (**RISC-V LP64D ABI** и **System V AMD64 ABI**) требуют выравнивания указателя стека `sp` / `rsp` по границе **16 байт** для корректной работы 128-битных типов и векторных регистров (на x86-64 невыровненные векторные команды вызывают исключение), атомарных операций и предотвращения пересечения границ 64-байтных кэш-линий.

## Контрольные вопросы

**1. Почему в RISC-V нельзя одной инструкцией загрузить значение из памяти и сложить его с регистром, а в x86 можно? Чем за это платит x86?**
* **RISC-V** построен по принципу **Load/Store (RISC)**: все инструкции имеют фиксированную длину 32 бита, а арифметико-логическое устройство (АЛУ) работает исключительно с регистрами. Чтобы сложить число из памяти с регистром, нужны две отдельные команды (`ld`/`fld` + `add`/`fadd.d`).
* **x86-64** — это **CISC-архитектура** с адресацией «регистр–память», поэтому одна инструкция может одновременно читать операнд из памяти и выполнять операцию (`add rax, QWORD PTR [rdi]`, `mulsd xmm0, QWORD PTR [rax]`).
* **Чем за это платит x86-64:** инструкции имеют переменную длину (от 1 до 15 байт) и сложные режимы адресации. Это требует громоздкого, дорогого и энергозатратного **декодера инструкций** (который вынужден на лету определять границы команд и разбивать сложные CISC-инструкции на простые внутренние микрооперации $\mu$-ops).

**2. Сравните внутренние циклы `ijk` и `ikj`: какие обращения к `b` идут подряд, а какие с шагом в строку?**
* В **`mul_ijk`** внутренний цикл идёт по индексу `k`: элементы `a[i][k]` читаются подряд (`+8` байт), а обращения к **`b[k][j]` идут по столбцу с шагом в целую строку (`6144` байта** = `768 * 8` байт; инструкции `add rax, 6144` на x86-64 и `add a5, a5, a2` на RISC-V), что вызывает промахи кэша почти на каждой итерации.
* В **`mul_ikj`** внутренний цикл идёт по индексу `j`: элемент `a[i][k]` загружается в регистр до начала цикла, а обращения к **`b[k][j]` (и к `c[i][j]`) идут строго подряд по одной строке с шагом `+8` байт**, полностью используя 64-байтные кэш-линии.

**3. Как в ассемблере Штрассена видны рекурсивные вызовы и накладные расходы на кадры? Почему на маленьких матрицах это может съесть выигрыш от меньшего числа умножений?**
* **Рекурсивные вызовы** видны в теле `strassen_rec` как **7 отдельных инструкций `call strassen_rec`** (по одной на каждое произведение $M_1 \dots M_7$).
* **Накладные расходы на кадры** видны в прологе/эпилоге (`sub rsp, 232` + 6 `push` = `280` байт на x86-64; `addi sp, sp, -304` = `304` байта и сохранение `ra, s0..s11` на RISC-V), в передаче 7-го и 8-го аргументов через стек в x86-64 (`push`/`pop` перед и после каждого `call`), а также в десятках инструкций `mov`/`sd`/`ld` (*register spilling*), сохраняющих указатели подматриц в стек перед каждым рекурсивным вызовом и загружающих их обратно.
* **Почему проигрывает на маленьких матрицах:** вместо 8 умножений Штрассен делает 7, но добавляет **18 матричных сложений/вычитаний** (циклы `.L10`–`.L38`), сборку 4 блоков и 7 рекурсивных вызовов. На маленьких матрицах ($n \le 64$) время на работу с временными буферами в памяти и обслуживание стековых кадров превышает экономию от одного пропущенного умножения.

**4. Сравните `max2` на x86 и RISC-V: где компилятор обошёлся `cmov`/`slt`, а где условным переходом? Почему на x86 ответ может зависеть от компилятора и флагов?**
* В **`max2`**:
  * На **x86-64 (`-O2`)** условных переходов нет — используется инструкция условной пересылки **`cmovge eax, esi`**.
  * На **RISC-V (`-O2 -march=rv64gc`)** компилятор ставит условный переход **`bge a1, a0, .L2`**, так как в базовом наборе `rv64gc` нет инструкции `cmov`, а короткое ветвление оказывается эффективнее последовательности с `slt`.
* **Почему на x86-64 результат зависит от компилятора и флагов:**
  * При отключённой оптимизации (`-O0`) или при сборке под старые целевые архитектуры без поддержки CMOV (например, `-march=i386`) компилятор генерирует обычный условный переход (`jge`/`jl`).
  * Даже при `-O2`/`-O3` эвристика компилятора (GCC и Clang имеют разные модели стоимости) может выбрать переход вместо `cmov`, если вычисление веток содержит обращение к памяти (которое могло бы вызвать *Segmentation Fault* при безусловном вычислении) или если компилятор считает ветвление хорошо предсказуемым, поскольку `cmov` заставляет процессор всегда вычислять оба значения и создаёт дополнительную зависимость по данным.

**5. Почему программу, собранную для x86-64 в 2005 году, можно запустить на процессоре 2025 года, а собранную с `-march=native` не всегда?**
* **Обратная совместимость ISA:** архитектура x86-64 проектировалась с жёстким требованием обратной совместимости — все базовые инструкции архитектуры x86-64 (Baseline, вышедший в 2003–2005 годах) поддерживаются каждым современным процессором x86-64. Поэтому программа 2005 года использует только базовый набор команд и без проблем исполняется на процессоре 2025/2026 года.
* **Специализация при `-march=native`:** этот флаг разрешает компилятору использовать все новейшие векторные и аппаратные расширения именно той модели CPU, на которой выполняется компиляция (например, `AVX2`, `FMA`, `AVX-512`, `BMI2`, `SHA`). Если перенести такой исполняемый файл на более старый процессор или на процессор другого производителя без этого расширения (например, с процессора с `AVX-512` на процессор только с `AVX2`), при встрече неподдерживаемой инструкции процессор сгенерирует аппаратное исключение **Illegal Instruction (`SIGILL`)** и программа аварийно завершится.
